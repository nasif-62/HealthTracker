§1 & §2 — Overview & Architecture

Project Overview & Architecture

A personal, offline-first health management app for a single user. No cloud dependency in MVP.

What the App Manages

DomainWhat It Tracks
MedicinesStock, schedule, dose logging, reminders
Health MetricsWeight, BP, sugar, heart rate, SpO2, temperature
Medical RecordsPrescription photos, lab reports, scans (JPG / PDF)
Doctor VisitsConsultation history, diagnoses, follow-ups
TimelineUnified chronological view of all health events

Core Principles

PRINCIPLE 1
Offline First — 100% functional with no internet. No feature may depend on network access.
PRINCIPLE 2
Immutable History — Records are never deleted or overwritten. Changes produce new records.
PRINCIPLE 3
Single User — No login, no accounts. All data belongs to one person on one device.
PRINCIPLE 4
Data Separation — Binary files → file storage. SQLite stores structured data only. Never raw bytes in DB.

Database Schema & ERD

All structured data lives in SQLite. Images/PDFs live in file storage. The DB stores only file paths.

Entity Relationship Diagram

ERD

6.1 Medicine Management — Dose Flow

1
User adds a medicine
Name, dosage, stock, start/end date, instructions, 1+ schedule times
2
MedicineService.AddMedicine() called
Validates → saves Medicine row → saves MedicineSchedule rows → calls ReminderService.ScheduleReminders()
3
User taps "Take Now"
MedicineService.LogDoseTaken(medicineId, scheduleId) is called
4
Stock deducted automatically
StockCount = StockCount − DoseAmount. MedicineLog created with WasTaken=1, StockBefore/After recorded.
Stock Rules
// Deduct only when WasTaken = 1 StockCount = StockCount - DoseAmount // NEVER go below zero — warn + confirm before logging if (StockCount < DoseAmount) → warn user, require confirmation // Low stock warning badge threshold if (StockCount <= DoseAmount × 5) → show warning badge // Skipped doses: log created, stock unchanged WasTaken = 0 → StockCount stays the same

6.2 Reminder System

Notification Rules
// Unique notification ID formula NotificationId = MedicineId × 1000 + ScheduleId // On every app launch — re-register all active reminders ReminderService.RescheduleAll() // Cancel reminders when any of these occur: // · Medicine.IsActive set to 0 // · Medicine.EndDate has passed // · A specific schedule time is deleted // · User manually disables reminders

§9, §10 & §11 — Business Rules, Data Rules & Security

Rules & Security Model

Business Rules — Enforced in Service Layer Only

RULE-01
A medicine cannot have zero schedule times. Minimum 1 schedule required before saving.
RULE-02
StockCount must never go below 0. Warn user and require confirmation if insufficient stock.
RULE-03
Every MedicineLog must reference a valid MedicineId and ScheduleId. No orphan logs.
RULE-04
HealthMetric values must pass range validation before saving. See §6.3 for all ranges.
RULE-05
MedicalReport.FilePath must point to a file that exists. Verify copy succeeded before saving record.
RULE-06
DoctorVisit.FollowUpDate, if provided, must be today or a future date. Reject past dates.
RULE-07
MedicineLog records are NEVER deleted. They are permanent, immutable historical records.
RULE-08
HealthMetric records are NEVER deleted. Each entry is immutable once saved.
RULE-09
Setting Medicine.IsActive = 0 must immediately cancel ALL reminders for that medicine.
RULE-10
On every app launch, ReminderService.RescheduleAll() must be called to survive device reboots.

Data Mutability Rules

TableRuleWhat's Allowed
MedicineLogImmutableNever UPDATE or DELETE rows
HealthMetricImmutableNever UPDATE or DELETE rows
MedicineMutableAllow UPDATE (stock, IsActive). Never hard DELETE.
DoctorVisitMutableCan add notes, follow-up date. Never hard DELETE.
MedicalReportDeletableHard delete allowed — remove DB row AND file.
📅
DateTime Storage Standard
Date only: "YYYY-MM-DD"  ·  Datetime: "YYYY-MM-DDTHH:mm:ss"  ·  Always parse with DateTime.Parse(s, CultureInfo.InvariantCulture)

Security — PIN Lock Flow

1
App launches cold
Check SecureStorage (platform keychain) for configured PIN
2
No PIN → go to Shell normally
User can configure a 4–6 digit PIN at any time in Settings
3
PIN configured → show full-screen blocking overlay
Shell not accessible until correct PIN entered. Resume from background <2min skips check.
4
5 failed attempts → 30-second cooldown
Input disabled during cooldown. Timer displayed. All files in AppDataDirectory — private to app.

§12, §13 & §14 — Backup, Error Handling & MVP Scope

Backup, Errors & MVP Scope

Backup File Structure & Flow

ZIP Structure & BackupService Flow
HealthBackup_2026-03-06.zip ├── healthapp.db └── files/ ├── reports/ ├── prescriptions/ ├── scans/ └── other/ // BackupService.CreateBackup() → Create temp folder → Copy healthapp.db into temp → Copy entire /HealthApp/ file directory to temp/files/ → Compress temp folder → .zip with date in filename → Use MAUI Share API (Google Drive, email, etc.) → Delete temp folder after share completes

Error Handling — ViewModel Pattern

C# — Standard ViewModel Error Pattern
// Every ViewModel exposes these 3 observable properties: bool HasError { get; set; } string ErrorMessage { get; set; } bool IsBusy { get; set; } // All service calls in ViewModels follow this exact pattern: IsBusy = true; HasError = false; try { await _service.DoSomething(); } catch (Exception ex) { HasError = true; ErrorMessage = "A friendly message for the user"; // Log full exception details internally } finally { IsBusy = false; }
⚠️
Error Handling Rules
Never silently swallow exceptions. File I/O errors → user-friendly message, no crash. Validation errors → inline under input field, never popups. Notification failures → log only, do not block the save flow.
